## Why a separate agent

Quiver produces governed procedures and flowcharts. Presentations need a different planning and validation path: slide selection, page capacity, visual fit, and editable PowerPoint structure. I built AgentEdge Slides as a separate agent within the broader Quiver platform, with its own identity and state instead of treating a deck as another document export.

## My contribution

I led the Slides agent and its platform integration. The implementation includes a dedicated agent workspace and control plugin, a Python presentation pipeline, a template and layout catalog, source staging, session isolation, and shared Teams delivery controls. I also worked on quality and lifecycle fixes after the initial scaffold.

The model chooses the message, content, and suitable layout. Deterministic code then maps those choices into an approved template, builds an editable PPTX, renders every slide, checks content coverage and fit, and requires visual review before delivery. A revision creates a new artifact version rather than overwriting the prior one.

## Reliability and scope

The agent keeps source files and delivery state separate from Quiver's. Consent and upload callbacks distinguish a permission card from a completed file transfer, while idempotent delivery and resend controls reduce duplicate sends. Local qualification covers real slide builds and rendering, state transitions, and synthetic Teams transport.

The available platform notes still list live Teams UI acceptance and rollout gates as pending. I describe the agent as built and locally qualified, without claiming a completed production launch.

## Interview summary

I built a dedicated presentation agent inside the Quiver platform. It turns source material into editable, brand-template PowerPoint decks, then checks layout and rendered slides before consent-aware delivery. The engineering focus was trustworthy artifacts, isolated state, and recoverable delivery rather than text generation alone.
